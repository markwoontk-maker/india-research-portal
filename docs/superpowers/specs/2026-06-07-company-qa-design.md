# Company-tab Bull / Bear / Key-Debate Q&A — Design

**Date:** 2026-06-07
**Status:** Approved (design); pending implementation plan

## Goal

Add a new card to the **Company tab** that, per company, surfaces a set of
**stock-driver and downside-risk questions** with **grounded, cited answers**.
Two "agents" produce the content: a **questioner** that asks company-specific
questions, and an **answerer** that evaluates and answers them from the
company's NotebookLM broker-PDF sources.

## Constraints (inherited from the portal)

- **Static GitHub Pages site**, no build step. No paid/keyed APIs, ever. No
  secrets in the bundle. (See `CLAUDE.md`.)
- **Cloud routines cannot push to the repo** — anything that must commit runs
  from the **local** `daily-refresh.ps1` pipeline (Windows Task Scheduler).
- Live LLM calls in the browser are impossible (no key) → all content must be
  **pre-generated into a `data/*.json` file** the page fetches and renders.
- Answers are **grounded in NotebookLM notebooks only** (the user's broker-PDF
  library). Companies without a notebook get no Q&A.

## Scope

- **Selectable companies:** 234 entries in the `NOTEBOOKS` map in `index.html`.
- **Answerable companies:** the **78** that have a real notebook URL — only
  these have sources to ground answers. The miner only works on these; the
  remaining ~156 simply render nothing (no "notebook pending" noise).
- Company → notebook_id resolved from the `NOTEBOOKS` map (URL contains the id)
  or `C:\Users\admin\nlm_notebooks.csv` (source-of-truth map).

## Structure of the Q&A (per company)

Three sections, company-specific questions generated by the questioner:

- **Bull case** — ~3 questions on the upside drivers / what moves the stock up.
- **Bear case** — ~3 questions on the downside risks / what could break the thesis.
- **Key debates** — ~2 questions on open debates / what to watch.

Each answer is concise, ends with an inline `(Broker, MM/YY)` citation linking
to the source PDF (matching the existing convention in the Drivers/Thesis cards).

## Architecture

### Two agents, two prompt-driven passes, one orchestrator

A new gated build step `scripts/build-company-qa.ps1` (modeled on
`build-positioning.ps1`) runs **two distinct headless-Claude passes**, so each
agent is single-purpose and independently inspectable.

**1. Questioner agent** — `docs/company-qa-questioner-prompt.md`
- Input: the company → notebook_id list (from the `NOTEBOOKS` map / nlm csv).
- For each answerable company, calls `nlm notebook describe <id>` to see what
  the sources actually cover, then generates company-specific bull (~3),
  bear (~3), and key-debate (~2) questions.
- Output: `data/company_questions.json` — an intermediate, **hand-editable**
  file (schema below).
- **Edit preservation:** a company/question marked `"pinned": true` is never
  regenerated or reworded; the questioner only fills in companies that are
  missing or not pinned.

**2. Answerer agent** — `docs/company-qa-answerer-prompt.md`
- Input: `data/company_questions.json`.
- For each question, runs `nlm notebook query <id> "<question>" --json` against
  that company's broker-PDF sources, then **evaluates/synthesizes** the grounded
  result into a concise answer.
- Derives the `(Broker, MM/YY)` citation from the source NotebookLM cited,
  parsing the `[YYMMDD] [House] Folder - Thesis.pdf` filename pattern. If no
  clean source is identifiable, omits the citation (no fabrication).
- Output: `data/company_qa.json` (schema below).

> Open implementation detail to confirm in the plan: whether `nlm notebook
> query --json` exposes which source(s) were cited. If it does not, fall back to
> citing the company's most-recent source, or omit the citation. Citations are
> best-effort; their absence must not fail validation.

### Scale & cost control

~8 queries × 78 companies ≈ 600 `nlm` queries (each 10–60s) — too much for one
window. Therefore the answerer is **incremental + resumable**:

- Each company entry carries an `asOf` date.
- The answerer processes companies in a stable order, **skips any company
  already refreshed in the current fortnight window**, writes per-company as it
  completes, and **exits cleanly at the timeout** (partial progress persists).
- The next run (next day's `daily-refresh`, or next fortnight) continues where
  it left off. Load spreads naturally across runs.

### Gating & scheduling

- Gated **twice-monthly** (H1 on/after the 2nd, H2 on/after the 17th) via
  `scripts/.company-qa-state.json` (`lastWindow` watermark), exactly like
  `build-positioning.ps1`. Because the answerer is resumable, the watermark is
  only advanced once a window's full pass completes; a timed-out partial run
  leaves the watermark so subsequent daily runs in the same window keep going.
- Wired as a step in `daily-refresh.ps1`; its existing git step stages,
  commits, and pushes `data/company_qa.json` + `data/company_questions.json`.
- `--allowedTools Bash Read Write Edit` (+ the `nlm` CLI via Bash). No
  WebFetch/WebSearch needed — grounding is NotebookLM-only.
- Always `exit 0` so it never aborts the rest of the daily refresh.

## Data contracts

### `data/company_questions.json` (intermediate, hand-editable)
```json
{
  "asOf": "2026-06-07",
  "companies": {
    "Adani Power": {
      "notebookId": "2052a512-3b1a-4dd6-8ff4-f31a1250dbb3",
      "bull":    [ { "q": "…", "pinned": false } ],
      "bear":    [ { "q": "…", "pinned": false } ],
      "debates": [ { "q": "…", "pinned": false } ]
    }
  }
}
```

### `data/company_qa.json` (rendered by the page)
```json
{
  "asOf": "2026-06-07",
  "companies": {
    "Adani Power": {
      "asOf": "2026-06-07",
      "bull":    [ { "q": "…", "a": "…", "broker": "Jeff", "date": "260604", "url": "…" } ],
      "bear":    [ … ],
      "debates": [ … ]
    }
  }
}
```
- `broker`/`date`/`url` optional per item (best-effort citation; `date` is
  `YYMMDD` to match the existing cite formatter).

## Front-end (mirrors the existing Thesis / Drivers cards)

- New `#cQACard` in the Company-tab card stack, placed **right after the
  Bull/Bear Thesis card** (with the narrative cards, before Financials).
- Three labelled sections (Bull / Bear / Key debates). Items are
  **collapsible**: the question is always visible; clicking it expands the
  answer + citation. (Reuse existing card / chip / cite styling.)
- Loader: `window.COMPANY_QA = null;` + `fetch('data/company_qa.json',
  {cache:'no-store'})` → on success assign and call `renderCompanyQA()` — the
  same loader shape as `window.THESES`.
- `renderCompanyQA()` keyed on `currentCompany`; hidden for sectors and when the
  company has no entry. Called from the existing company-select handler
  alongside `renderCompanyThesis()` / `renderCompanyDrivers()`.
- A `.co-desc-src` footnote: "Questions generated per company; answers grounded
  in the company's NotebookLM broker-report library. Click a question to expand."

## Validation & safety

- `build-company-qa.ps1` snapshots file hashes, runs a Node validator on each
  output file, and **reverts an individual file on malformed JSON**:
  - `company_qa.json`: top-level `companies` object; each entry has `bull`,
    `bear`, `debates` arrays; each item has non-empty `q` and `a`.
  - `company_questions.json`: each entry has the three arrays; items have `q`.
- Citations are best-effort and never required by the validator.
- No new APIs/keys. `nlm` uses the existing `work` profile auth
  (markworktk@gmail.com). All static-site rules respected.

## Out of scope (YAGNI)

- Companies without a notebook (no source to ground answers).
- Web-search grounding (NotebookLM-only by decision).
- A cloud routine (cannot push; local pipeline only).
- Cross-company comparison / screening on the Q&A (per-company display only).
